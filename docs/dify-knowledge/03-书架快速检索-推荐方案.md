# 书架快速检索 — 推荐方案

> 所属模块: SHELF-001 (书架管理) | 版本: v1.3 | 状态: 更新反映 v1.2/v1.3 实现

## 方案选型

书架快速检索有三种可选方案，各自适用于不同场景：

| 方案名称 | 适用场景 | 优点 | 缺点 |
|------|------|------|------|
| 客户端过滤 | 书架中书籍数量少于 200 本 | 搜索零延迟、离线可用、不需要修改后端代码 | 首次加载需要一次性获取全量书籍数据 |
| 后端全文搜索 | 书架中书籍数量超过 200 本，或需要跨多个字段搜索 | 支持海量数据、不占用前端内存、可利用数据库索引 | 需要修改后端代码和数据库结构 |
| 混合方案（已实现） | 通用场景，渐进增强 | 兼顾性能与开发体验，小书架用客户端过滤，大书架自动降级为后端搜索 | 实现逻辑稍复杂，需要同时维护两套搜索路径 |

## 推荐方案：混合方案（✅ 已在 v1.2 中实现）

### 核心思路

书架页面首次加载时，一次性向后端请求用户的所有书籍数据（page_size=200，大多数个人用户的书架在 20 到 100 本之间）。获取全量数据后，后续的搜索和筛选操作全部在客户端内存中完成，实现输入即搜、零网络延迟。当用户书架数据量超过 200 本时，自动切换为后端搜索模式，以服务端分页查询作为降级方案。

### 为什么混合方案最适合本项目

本 App 是个人使用的工具，具有以下特征使混合方案成为最佳选择：
- 单个用户的书架通常在 20 到 100 本之间，数据量极小
- 全量加载 100 本书的 JSON 数据仅约 5KB，对网络和内存几乎没有负担
- 客户端过滤的搜索体验远优于 API 往返（输入即搜，无需等待网络请求）
- 200 本的阈值覆盖了几乎全部实际使用场景，后端搜索只作为极端情况的兜底

### 搜索行为规范（v1.2 实际实现）

搜索框的交互行为遵循以下规则，以平衡体验和性能：

| 输入字符数 | 触发的行为 | 原因 |
|------|------|------|
| 0 个字符 | 显示全部书籍，恢复正常的书架视图 | 等同于未搜索状态 |
| 1 个字符 | 不触发任何搜索 | 避免过早过滤，1 个中文字符的匹配范围太广 |
| 2 个或更多字符 | 触发防抖搜索（等待用户停止输入 300 毫秒后执行），优先使用客户端过滤 | 2 个字符开始具有足够的区分度 |
| 用户清空输入框 | 立即恢复全量书架视图，不等待防抖 | 清空是明确的取消搜索意图，应立即响应 |

## 客户端搜索模式的数据流（v1.2 已实现）

1. 用户进入书架页面，前端调用 GET /api/v1/books?page=1&page_size=200 一次性获取全量书籍数据
2. 全量数据存储到 Pinia Store 的 allBooks 数组中
3. 用户在搜索框中输入关键词，前端将输入转为小写后进行字符串包含匹配
4. 匹配范围包括书名的标题字段和作者字段
5. 匹配结果存入 filteredBooks 数组，书架列表实时切换为过滤后的结果
6. 如果后端返回的书籍总数超过 200 本，前端自动将搜索模式切换为服务端搜索

## 服务端搜索模式的数据流（v1.2 已实现）

当用户书架数据量超过阈值时，搜索流程如下：
1. 用户输入关键词后，前端调用 GET /api/v1/search?q=关键词 接口
2. 后端在数据库中同时对书名和作者两个字段执行 LIKE 模糊查询（使用 SQLAlchemy or_ 函数）
3. 后端返回分页后的匹配结果，前端直接渲染，不再做客户端二次过滤

## v1.3 新增：AI 语义搜索模式

在上述两种模式基础上，v1.3 新增了 AI 语义搜索作为第三种模式：
1. 用户在书架搜索栏切换到"🤖 AI 语义"模式
2. 输入自然语言描述（如"最近看的那本修仙小说"）
3. 前端调用 POST /api/v1/ai/search，后端通过 Dify LLM 语义匹配返回结果
4. 结果含 match_reason（匹配原因）和 score（匹配度百分比）
